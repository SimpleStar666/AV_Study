## 第 1 步：搭环境 ✅（已完成）

**做了什么**
- WSL2（Ubuntu-20.04，用户 ts）安装 ffmpeg 4.2.7 / ffprobe / ffplay / x264 / v4l-utils
- 下载 mediamtx v1.21.3（GitHub 直连不通，经 gh-proxy 镜像），安装到 /usr/local/bin/mediamtx，配置 /home/ts/mediamtx.yml
- 生成测试视频 /home/ts/test.mp4（testsrc，640×360@15fps，5 秒，H.264，28KB）

**学到了什么**
- ffmpeg 三件套分工：ffmpeg=生产（转换/推流）、ffprobe=检验（只读分析）、ffplay=展示（播放）
- **容器 ≠ 编码**：mp4 是容器（打包格式），H.264 是编码（画面压缩方式）
- 容器码率 vs 视频码率：差值来自 moov 盒等容器元数据开销（短文件占比高，长视频可忽略）
- testsrc 的意义：确定性测试源，不依赖设备，先把链路跑通

**验收结果**：mediamtx RTSP :8554 监听日志 ✅；ffprobe 读出容器/编码/分辨率/帧率 ✅；三问作答 ✅

## 第 2 步：摄像头挂进 WSL ✅（已完成）

**做了什么**
- Windows 安装 usbipd-win（USB/IP 共享服务，需 UAC）
- 绑定并挂载笔记本摄像头：`usbipd bind --busid 1-11` + `usbipd attach --wsl --busid 1-11`
- WSL 安装 usbip 客户端（linux-tools-generic），ts 加入 video 组
- 抓拍验证：`ffmpeg -f v4l2 -input_format mjpeg -video_size 640x480 -i /dev/video0 -frames:v 1 cap.jpg`

**学到了什么**
- v4l2（Video4Linux2）：Linux 摄像头统一接口，`/dev/video0` 是设备文件
- 摄像头能力表：BisonCam 支持 MJPG（压缩）/ YUYV（裸流），IPC 摄像头同理内置编码器
- 调摄像头基本功：先 `v4l2-ctl --list-formats-ext` 查能力 → 显式指定 `-input_format`
- usbipd 原理：USB/IP 协议把 USB 设备变成网络设备，attach 后 Windows 侧暂时失联

**验收结果**：v4l2-ctl --list-devices 无需 sudo ✅；自行抓拍 ✅；三问作答 ✅

## 第 3 步：H.264 编码 + RTSP 推流 ✅（已完成）

**做了什么**
- 链路自测：testsrc 合成源 → libx264 → RTSP → mediamtx → ffprobe 验证（读出 h264/640x360/15fps）
- 真摄像头推流：v4l2(MJPEG) 采集 → 解码 YUV → libx264 软编（H.264 / 2Mbps / zerolatency / GOP50）→ `rtsp://localhost:8554/live`
- ffplay 拉流成功看到实时画面

**学到了什么**
- 推流命令逐条拆解：`-re` / `-preset veryfast` / `-tune zerolatency` / `-b:v 2M` / `-g 50` / `-pix_fmt yuv420p`
- 推流-拉流架构：publisher → mediamtx 分发 → player
- 关键认知①：USB 摄像头输出 MJPEG 是带宽所迫（YUYV 720p@30 ≈ 55MB/s 超过 USB2.0 有效带宽 ~35MB/s），640x480 时 YUYV 才塞得下
- 关键认知②：真实 IPC = Sensor→ISP→片内 YUV→硬编码器(H.264/H.265)，YUV 不出芯片、无 MJPEG 环节；硬编源可用 `-c:v copy` 零转码推流
- `-re` 是输入侧限速器（`-i` 之前），只对文件/合成源有意义；实时采集设备不需要

**验收结果**：ffplay 实时画面 ✅；四问：GOP/zerolatency/localhost:8554/live 全对，-re 定位补课完成 ✅

- 用户抓包数据：OPTIONS→ANNOUNCE(SDP: m=video 0 RTP/AVP 96, a=rtpmap:96 H264/90000, sprop-parameter-sets=SPS/PPS)→SETUP(Transport: RTP/AVP/UDP;unicast;client_port=19710-19711;mode=record)→RECORD；722 个 RTP 包
- 关键发现①：**推流端握手是 OPTIONS/ANNOUNCE/SETUP/RECORD**，播放端才是 OPTIONS/DESCRIBE/SETUP/PLAY（ANNOUNCE 上报 SDP，RECORD 下令开播）

**验收结果（2026-10-27）**：五问 a/b/c/e 通过（b 追问"无 framerate 行但有帧率"获解答：帧率在 SPS VUI + RTP timestamp 中，DESCRIBE 场景才有 a=framerate）；d 补课：协议开销 = IP20+UDP8+RTP12 = **40B/包**，且 45-42 文件场景是容器开销、实时场景按 40B×每秒包数 计算 ✅

## 第 5 步：音画同步（A/V Sync）⏳（进行中）

**准备（已完成，已本地提交）**

- 双运行时验证：BOM+5.1 解析 OK；[B2] 查询对 step5.pcapng 实测 OK

**自测数据（step5.pcapng）**
- SDP 两个 m=：`m=video 0 RTP/AVP 96`（a=rtpmap:96 H264/90000）+ `m=audio 0 RTP/AVP 0`（**静态 PT 0 = PCMU，无需 rtpmap**）
- RTSP 流程：OPTIONS→ANNOUNCE→**SETUP streamid=0**→**SETUP streamid=1**→RECORD（每路媒体各一次 SETUP）
- 音频 RTP：PT=0，每包 timestamp +1024（8000Hz 时钟 × 1024 采样/包 = 128ms）
- 视频 RTP：PT=96，同帧多包同 ts（90000Hz 时钟）
- 关键认知：**静态 PT(0-95) 由 RFC3551 定义无需 rtpmap；动态 PT(96-127) 必须 rtpmap 声明**；每路媒体有自己的时钟域（视频90kHz/音频8kHz），播放端靠各自 timestamp 对齐 = 音画同步原理
